# 日志与运行观测决策

## 当前结论

项目当前不建设集中式日志平台、固定日志查询界面或主动告警系统。

现阶段采用以下方式即可：

1. 由 AI 或管理员按需、定期查询 Supabase 中的 `operational_events`。
2. 用户反馈错误时，优先根据接口返回的 `request_id` 定位对应事件。
3. 数据库事件不足以解释问题时，再查询服务器上 `human-draft-server` 的 systemd journal。
4. 运营指标继续使用 `product_events` 及现有运营统计能力，不复制成另一套异常日志。

这一选择是当前项目的明确运维决策，不是待补缺陷。后续评审和开发任务不应仅以“通用最佳实践”为理由，反复建议引入 Sentry、ELK、Grafana Loki、腾讯云日志服务、固定日志后台，或邮件、短信、微信等主动通知。

## 当前日志边界

`operational_events` 是关键异常事件表，不是全量请求日志。当前主要持久化：

- 服务端 5xx 错误；
- 请求限流；
- 图片存储额度超限；
- 注册关闭、系统只读等运行控制阻止事件。

事件保留请求编号、接口、状态码、安全错误摘要、错误指纹和发生次数，同类问题按小时聚合，默认清理 90 天以前的数据。不得记录请求正文、令牌、凭证或用户私人内容。

Fastify 的结构化请求日志输出到标准输出。线上服务由 systemd 托管，因此可通过 journal 查询启动、请求、异常和进程退出信息。数据库不可用、事件写入失败、Node 启动失败或进程崩溃时，应查 journal，而不能只依赖 `operational_events`。

## 建议检查方式

- 公测或低流量阶段：每周检查一次关键事件，或在用户反馈后即时查询。
- 用户量或变更频率增加后：可改为每天检查，但仍不要求建设固定界面。
- 汇总时重点查看新增错误、未解决错误、重复次数、受影响接口、影响用户数和近期趋势。

## 重新评估条件

只有出现具体运维需求时，才重新评估集中日志或主动告警，例如：

- 服务扩展为多个生产实例，单机 journal 已不便检索；
- 日志或异常事件量明显增加，AI 直接查询的效率或成本不可接受；
- 多名运维人员需要同时检索、共享和跟踪处理状态；
- 已发生多次因定期检查间隔而过晚发现的故障；
- 业务明确提出分钟级发现或响应时限；
- 合规、审计或客户要求需要更长留存和不可篡改记录。

在这些条件出现前，默认继续使用“AI 查询数据库事件，必要时查询服务器 journal”的轻量方案。
