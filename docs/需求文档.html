每个城市下面可以分别记录“想去”和“去过”的地点，支持新增、编辑名称和简短备注、切换状态与删除。

城市和地点都按登录用户隔离并保存到云端。当前地点数据包含城市编码、名称、备注、状态与创建更新时间。

当前不便

新增地点前，要先确认地点在哪个省市，再展开省份、找到城市、进入地点页面，操作路径偏长。

当前不便

系统无法根据名称提供候选结果，也不知道地址、经纬度和行政区归属，容易出现重名或归错城市。

尚未实现

跨城市汇总

目前没有一张跨城市的“全部想去地点”或“全部去过地点”清单，这属于可继续讨论的后续能力。

问题与目标

目标不是获取用户的实时位置，而是理解用户主动输入的地点属于哪里。

方案已确认
“我输入广州的白鹅潭，系统能找到对应地点，知道它属于广东省广州市，然后让我直接加入想去或去过，而不是让我先查省市、再进入广州添加。”

这是一项全国范围的地点检索与行政区自动归类能力，与读取用户当前位置无关。

减少寻找路径

用户从全国足迹入口直接开始搜索，不需要先知道地点属于哪个省市。

避免错误归类

由地图地点数据返回省、市、区和行政区划编码，系统自动匹配自己的城市数据。

保留用户控制

系统提供候选结果，但由用户确认具体地点和“想去 / 去过”状态；找不到时仍能手动添加。

建议的完整用户流程

全国搜索应作为独立入口，城市内部的手动记录继续保留，两种方式最终写入同一份地点数据。

推荐方案
打开全国搜索

在“全国足迹”页面点击搜索或新增地点入口，进入专用的地点搜索页。

输入地点名称

例如输入“白鹅潭”。至少输入两个字并短暂停顿后，才请求候选结果。

确认具体地点

列表展示地点名、详细地址以及省市区，用户从重名结果中选择正确地点。

选择记录状态

选择“想去”或“去过”，可以补充一条简短备注，然后确认保存。

自动归入城市

系统按照行政区编码写入正确城市，并回到结果页或展示保存成功的位置。

入口建议

全国足迹页提供醒目的“搜索地点”入口；城市地点页原来的加号继续用于手动添加。以后如果搜索成为最常用入口，再决定是否把加号默认改成搜索。

编辑载体

地点搜索包含检索、候选列表和确认流程，应使用独立页面。选中地点后的“状态 + 简短备注”属于紧密相关的短编辑，可以使用底部 app-dialog；不使用居中输入弹窗。

地点与城市的业务规则

地点状态与城市点亮不是完全相同的概念，需要避免把“想去”误算成“去过”。

核心规则
  • 新增“想去”地点：地点归入对应省市，但城市保持当前状态；如果城市尚未去过，不能因此被点亮。
  • 新增“去过”地点：地点归入对应省市，同时自动点亮所属城市，因为去过一个具体地点就说明去过这个城市。
  • 想去改成去过：更新地点状态，并在城市还未点亮时自动点亮城市。
  • 去过改回想去或删除：不自动取消城市点亮。用户可能去过该城市的其他地方，取消城市足迹必须由用户主动操作。
  • 城市已经去过，新增想去地点：城市仍保持去过；地点单独显示在该城市的“想去”清单中。
  • 同一地点重复添加：优先使用地图 POI 标识判断重复；没有可靠标识时，以城市、名称和地址辅助提示，由用户决定是否继续添加。
  • 地图没有结果：允许用户选择省市后手动填写地点名称和备注，保证小众地点、临时展览和非标准名称仍可记录。

尚未决定：是否给城市增加独立的“想去”状态。现有城市只有“去过 / 未去”，第一期搜索功能不必为此改变城市数据模型；可以先通过地点数量或“有想去地点”标识表达。

当前推荐腾讯位置服务 WebService，而不是微信实时定位或微信原生附近选点。

完整实施方案

以下是未来决定开发时的工程范围，现在仅记录，不执行数据库迁移或接入第三方服务。

待排期
阶段一 · 开通服务 注册腾讯位置服务个人开发者，创建应用与 Key，开启 WebServiceAPI，分配关键词提示额度。
阶段二 · 服务端代理 由现有 Node 服务请求腾讯接口，加入超时、错误映射、缓存、用户限流和安全日志。
阶段三 · 数据升级 为地点增加来源、POI 标识、标准地址、省市区、行政区编码、经纬度等字段，并迁移现有手动数据。
阶段四 · 小程序体验 增加全国搜索页、候选结果、状态确认、自动归类、重复提示和手动添加兜底。

服务端职责

  • 新增登录后可用的地点建议接口，小程序只请求自己的服务器，不直接接触腾讯地图 Key。
  • 过滤和规范关键词，设置最短长度、最大长度、超时、每用户频率限制和全局并发保护。
  • 把腾讯返回结果转换成项目内部稳定格式，不让小程序依赖第三方原始字段。
  • 校验腾讯返回的城市编码能否匹配项目现有城市表；遇到直辖市、港澳台或行政区调整时明确处理。
  • 保存时由服务端重新校验省市归属，不能完全信任客户端提交的行政区信息。

迁移和兼容原则
  • 上线前先审计开发数据库里的地点数量、城市分布和代表性记录。
  • 保留所有现有地点名称、备注、状态、城市归属及创建更新时间，不因增加地图字段删除或重写用户含义。
  • 新字段允许现有手动记录为空；不保留两套地点表，也不建立长期双写。
  • 迁移完成后，所有新旧地点继续通过同一套列表、编辑、状态切换和删除接口操作。

费用、个人身份与配额

以下记录基于腾讯位置服务官方配额页 2025-11-13 更新的公开规则；真正实施前应再次核对。

当前结论

个人可以申请

使用个人实名认证即可创建个人开发者应用，不需要营业执照，也不需要先购买商业授权。

基础额度

关键词输入提示接口的个人开发者基础额度为每天 6,000 次，并发额度为每秒 5 次。

超过不会自动扣费

达到额度后请求会被限制或失败，不会自动产生账单。界面必须降级到手动添加，而不是阻止记录。

个人提额不作依赖

官网没有承诺个人开发者可免费提升到更高额度，因此产品设计按每天 6,000 次以内可持续运行。

商业授权门槛高

额外流量包只向已办理商业授权的客户开放；当前公开商业授权基础版为 50,000 元/年，默认主体为企业或组织。

当前规模足够

按一次完整搜索平均产生 3 次请求估算，每天约能承载 2,000 次地点搜索。现阶段无需为配额办理企业主体。

节省配额的固定措施

  • 至少输入两个汉字后才发起请求，停止输入约 500 毫秒后搜索。
  • 新输入产生时取消旧请求，只处理最后一次有效结果。
  • 相同关键词和结果短时间走服务端缓存，不重复请求腾讯。
  • 限制单个用户与单个 IP 的搜索频率，避免误触、脚本或恶意请求耗尽公共额度。
  • 监控每日调用量、失败率与限流状态；接近上限时优先收紧搜索频率，而不是产生不可控费用。

官方参考：配额说明、商业授权。

隐私、安全与失败兜底

这项功能处理的是用户输入的关键词和用户选择的地点，不读取用户当前位置。

必须遵守
微信权限

只做全国关键词搜索时，不调用 wx.getLocation、wx.chooseLocation 或 wx.choosePoi，因此不申请实时定位权限，也不弹定位授权。

Key 保护

腾讯位置服务 Key 只存放在腾讯云服务器的受限环境变量中，不写入小程序、不提交 Git、不记录到业务日志。优先配置服务器出口 IP 白名单或签名校验。

第三方失败

搜索超时、无结果、配额不足或腾讯服务不可用时，明确提示原因，并提供“手动选择省市后添加”的入口；已经保存的地点不受影响。

数据最小化

只保存用户最终选择的地点结果，不保存完整输入过程和未选择的候选列表。调用统计只记录次数、耗时和错误类型，不记录私人备注。

第一期验收标准

未来真正开发时，以下条件全部满足才算功能完成。

实施时执行
  • 用户能从全国足迹直接搜索“白鹅潭”等地点，不需要提前选择省份和城市。
  • 候选结果清楚展示地点名、地址和省市区，重名地点可以区分。
  • 选中地点后能记录为“想去”或“去过”，并可填写一条简短备注。
  • 地点自动写入正确城市；“想去”不会点亮城市，“去过”会自动点亮城市。
  • 直辖市、普通地级市、自治州以及港澳台现有城市编码都能正确匹配或明确降级。
  • 重复地点会给出提示，不会在用户无感知的情况下连续创建重复记录。
  • 腾讯搜索无结果、超时或超额时仍能手动添加地点。
  • 小程序代码与网络响应中不暴露腾讯位置服务 Key。
  • 不申请用户实时定位权限，隐私说明准确描述地点关键词和已选择地点的处理。
  • 迁移前后的现有地点数量、名称、备注、状态和城市归属一致，没有丢失业务数据。
  • 通过足迹聚焦测试、完整服务端回归、类型检查、UI 颜色测试和差异格式检查。
  • 体验版在真机完成搜索、保存、状态切换、重复提示、手动兜底和错误状态验收。
