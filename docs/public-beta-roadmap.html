上传保护与成本取舍

  • 服务端把普通图片上传硬上限设为 5 MB；即使环境配置误设得更高，也不会越过该上限。小程序裁剪后的正常图片通常低于此值，超过时提示用户缩小后重试。
  • 服务端在解码前限制图片总像素为 5,000 万，防止尺寸异常但压缩包很小的图片消耗过多内存。客户端裁剪不能替代这项服务端保护。
  • 所有规格都只缩小、不放大小图。WebP 使用有损颜色压缩，但透明通道使用更高质量，避免透明菜图边缘明显劣化。

  • 单图方案会让列表下载的文件大于专用小图，因此公测后仍要监控缓存命中、列表流量、加载时间和每用户图片字节。只有真实流量证明列表下载成本或体验成为主要问题时，才重新评估派生图；重新评估不等于预先承诺一定增加。

新增待办 · 接口性能与登录会话优化（2026-08-14，待完成）

产品决定：支持多设备登录，但不无限保留会话。每个用户最多保留 3 个有效设备会话；超过上限时自动撤销最早的会话。普通业务接口不应在每次请求前串行查询 Supabase 会话和用户表。

现状与根因

  • 近期线上日志中的普通接口已经出现数秒级耗时；健康检查只有毫秒级，说明主要瓶颈不在 Node 进程本身，而在业务请求的远程数据库调用链。
  • 当前每次业务请求都先使用不透明令牌查询 app_sessions，再查询 app_users，完成身份确认后才开始真正的业务查询。多个跨网络请求串行叠加，使保存、删除和页面初始化都能明显感到等待。
  • 部分写入操作成功后还会重新拉取整页或完整列表；上传图片等流程又包含额外网络步骤，进一步放大了等待时间。
  • 服务端与 Supabase 不在同一网络区域时，业务查询本身仍会承受跨区域往返延迟。认证优化可以去掉每个请求固定增加的两次查询，但不能代替后续的数据库区域与部署位置评估。

目标会话架构

  • 登录或刷新成功后签发短时有效、由服务端签名的访问令牌；普通业务接口只在 Node 服务内验证签名、有效期和必要声明，不再查询会话表和用户表。
  • 长期刷新令牌只保存哈希值，并继续由 app_sessions 管理。只有登录、续期、退出登录和设备管理需要访问会话表。
  • 每个用户最多保留 3 条有效刷新会话。新设备登录超过上限时删除最早会话，并提供“退出当前设备”和“退出其他／全部设备”的能力。
  • 访问令牌保持较短有效期；撤销刷新会话后，不再允许获得新访问令牌。需要立即阻断的高风险操作应另行设计更严格的会话校验，不能假设删除刷新会话会立刻使已签发的访问令牌失效。
  • 头像、昵称等资料只由账号资料接口读取，不参与每个业务请求的身份验证。定时清理已经过期的会话记录，避免历史登录无限累积。

接口与页面优化

  • 保存和删除成功后优先局部更新页面状态；只有服务端返回信息不足或数据依赖确实复杂时，才重新加载完整列表。
  • 合并可合并的 Supabase 查询，减少串行往返；需要原子一致性的多步写入放到一次事务或数据库函数中完成。
  • 页面只保留一套加载反馈，避免原生 loading、自定义 loading 和骨架屏同时出现；模块初始化中的独立请求应并发执行，并为首屏和后台刷新区分加载状态。

当前判断：现有方案已经具备私有 COS、数据库对象台账、短时签名访问、微信内容检测、服务端像素与文件大小限制、WebP 压缩和随机对象路径；但“小程序上传到 Node → 内容检测 → Sharp 压缩 → Node 上传 COS → 写数据库 → 签发图片地址”仍发生在同一次请求中。下一步重点是拆分上传、处理、业务引用和删除回收，不再重复建设基础用量台账。

目标上传与处理流程

  1. 小程序先调用上传初始化接口；服务端完成登录、模块权限、文件类型、当日次数和空间额度预检，创建状态为 pending 的图片资产记录，并分配不可覆盖的 asset_id 和对象键。
  2. 服务端只返回允许写入该对象或该用户临时目录的短时预签名上传地址／最小权限 STS 凭证。腾讯云永久密钥继续只保存在受信任的服务端，绝不进入小程序包。
  3. 小程序把原始文件直接上传到私有 COS 的 staging 前缀，不再把完整图片经 Node 中转；页面显示独立上传进度，失败后可以重新申请凭证重试。
  4. 上传完成后由完成接口或 COS 对象创建事件触发后台任务。后台以实际文件字节重新验证格式、尺寸、像素、文件大小和内容安全，并完成自动旋转、去除不必要元信息、缩放和 WebP 编码；客户端声明不能替代服务端验证。
  5. 处理成功后把正式对象写入不可变版本路径，将资产状态改为 ready，再允许业务记录引用；失败时记录 rejected 或 failed 和可安全展示的原因，不创建半完成业务记录。
  6. 业务列表只返回已经授权且状态为 ready 的资产；私有 COS 继续使用短时签名访问，签名地址只作为临时展示凭证，数据库保存稳定对象键或 asset_id，不保存带签名 URL。

图片版本与模块策略

  • 菜品、店铺、活动、衣橱和影视封面建议保留一张当前高清主图，并增加一张最长边约 480 像素的列表图；详情和打印使用主图，列表、选择器和小卡片只加载列表图，避免在几十像素的控件中下载 1080～1536 像素图片。
  • 普通业务图片的上传源文件只作为临时处理输入，正式主图和列表图校验成功后由生命周期规则延迟清理，不长期重复占用空间。
  • 关键节点属于不可替代的个人纪念照片，应单独确定原图保留政策：推荐保留私有原始文件或无二次损失的归档主图，再生成展示主图和列表图；不能默认只剩一张有损 WebP。
  • 头像使用带版本号的新对象路径，数据库切换成功后再延迟删除旧版本，不继续覆盖固定的 avatar.webp，避免缓存未刷新和更新失败后无法回退。
  • 若采用腾讯云数据万象按需生成列表图，必须同时评估图片处理费用、缓存命中和私有签名参数；在真实流量证明更合适前，优先使用规格固定、可核验的持久化列表图。

统一图片资产与可靠清理

  • 扩展现有 image_assets，补充资产 ID、处理状态、源对象键、主图／列表图对象键、宽高、内容指纹、错误状态和完成／删除时间；所有读取继续校验当前用户归属。
  • 业务表逐步改为引用 asset_id，上传处理和业务保存不再依赖一条请求中的临时 COS 路径。对象键必须包含用户、资产编号和不可变版本，不允许用户指定任意桶或任意路径。
  • 删除业务记录时先解除引用并把资产标记为 pending_delete；后台在宽限期后确认没有其他引用再删除 COS 对象。COS 删除失败进入重试队列，不因为一次网络失败永久遗留孤儿文件。
  • 定时任务扫描长期停留在 pending／processing 的任务、未被数据库引用的对象和删除失败记录；COS 生命周期只自动清理明确隔离的临时前缀，不直接对正式用户图片使用宽泛删除规则。
  • 上传、替换和删除必须记录资产编号、模块、处理耗时、源字节、输出字节和结果状态，但不得记录图片内容、永久密钥、完整签名地址或其他用户隐私。

完成标准与迁移边界

  • 普通上传不再占用 Node 服务器承接完整图片的入口和出口带宽；上传进度、后台处理和业务保存具有独立状态，弱网重试不会重复创建业务记录或覆盖已有图片。
  • 验证越权对象键、过期凭证、伪造 MIME、损坏图片、超大小、超像素、内容检测失败、COS 成功但数据库失败、数据库成功但旧图删除失败及任务重复投递等场景。
  • 列表页确认实际加载列表规格，不再下载高清主图；对比改造前后的上传完成时间、接口耗时、列表首屏时间、COS 存储量、处理次数和下行流量。
  • 基础 image_assets 已创建并完成 471 个有效对象回填；本条仍未启用客户端直传、COS 事件、数据万象处理、后台任务或生命周期删除。实施进阶状态机前必须基于现有台账设计原子迁移，不能另建重复统计表。
  • 在本待办正式上线前，现有“服务端同步压缩、每个模块只保存一张处理后图片”的规则继续有效；不能只实现客户端直传就删除现有服务端验证、内容安全检查或私有访问控制。

达到发布门槛后的阶段路线

1 发研发笔记，开放自然用户 不必在笔记里主动公开小程序入口，但搜索到或前来咨询的用户可以正常注册使用。 小范围获客

这一阶段做什么

  • 开始发布小红书研发手记，记录产品思考、解决的问题和研发过程。
  • 用户通过图片、微信搜索、朋友分享或主动咨询找到小程序后，可以直接注册使用。
  • 公测期所有新用户获得统一的 public_beta 权益，不给注册用户启动个人 30 天体验倒计时，也不在会员底座建成前手工发放正式体验权益。
  • 公测权益可以开放计划中的核心功能，但仍受单文件、每日上传、总空间和异常使用等安全硬上限保护。
  • 记录注册来源、公测批次和首次产生有效记录的时间，不采集用户私人内容。
  • 在“我的 / 关于”持续显示公测说明；不展示具体价格，不使用“永久免费”描述，也不把收费提示做成首次打开时的强制弹窗。
  • 每天查看激活、留存、错误、异常流量、文件空间和数据库增长。

进入下一阶段

出现一批完成注册并产生真实记录的早期用户，系统没有数据隔离、保存失败或成本失控问题。

2 边使用边优化 30～45 天 优先解决真实问题，同时观察留存和资源成本。 产品验证

优先级顺序

  1. 保存失败、数据错误、隐私和性能问题。
  2. 阻碍用户完成核心流程的体验问题。
  3. 高频用户真实提出的功能改进。
  4. 新的模块灵感和低优先级美化。

必须观察

  • D7、D30 留存，以及用户回来使用的频率。
  • 单模块用户和跨模块用户的比例。
  • 每个模块主要记录数的 P50 / P80 / P90，用来制定免费数量限制。
  • 每用户图片数、处理后实际字节数、数据库容量、下载流量和月成本。
  • 用户在哪些高级能力上真正感受到价值。
  • 重度与异常用户是否触发单文件、每日上传、接口频率和总空间保护。

同期完成的成本保护

  • 图片限制最大边长和总像素，使用有损 WebP；所有模块只保存一张处理后图片，列表、详情与打印共用该文件。持续观察列表流量、缓存和加载时间，再由真实数据判断是否需要改变单图策略。
  • 替换和删除文件时正确释放额度，定期对账孤儿文件，并为历史图片安排兼容迁移。
  • 按用户和模块核算文件空间，查询分页并补齐 user_id 索引；私有文件使用受控访问。

进入下一阶段

至少取得一轮 30～45 天真实使用数据，能够识别核心用户和主要成本来源。

3 落地免费版、体验版与会员底座 商业框架已经确定，用真实数据补齐各模块的具体免费数量。 权益工程

身份与用户 ID

以稳定的内部用户 ID 作为主身份、权益和未来订单的关联依据。不要使用昵称或 OpenID 人工匹配；OpenID 仅在对应 AppID 下稳定，未来由 auth_identities 完成身份映射。

权益数据

建立 membership_products、user_memberships、membership_orders 和 membership_grants。权益只需免费、体验和年费，暂不加入月费和永久会员。

管理员工具

分成“官方订单查询／售后”和“测试、赠送、补偿发放”两个入口。公测期只启用后者；查询用户后展示昵称、用户 ID、状态、到期时间和空间用量，再预览变更并用全局 app-dialog 确认。

用户可见信息

“我的”页面展示可复制的用户 ID、当前方案、到期时间、空间已用 / 总额和权益说明；另设简明收费说明，不等到收费当天才通知。当前公测先接入腾讯云 COS 的账号实际图片字节与图片数量，总额度仍显示为根据真实使用情况待定，不把 100 MB、2 GB 等内部假设提前承诺给用户。

条款与退款

建立可追溯的服务条款版本、订单权益快照和独立退款记录。付款前展示期限、退款边界与停服处理；退款不能靠删除订单或负数加天实现。

服务端规则清单

  • 按真实数据确定每个模块的“主要记录”免费上限；不是每使用一次扣费，也不拆成逐模块购买。
  • 为未来官方虚拟支付预留订单金额、商品、支付渠道和平台交易号；金额统一以整数最小货币单位存储，状态至少覆盖待支付、已支付、已履约、已关闭和已退款。
  • 订单保存购买时的商品名称、权益、期限、价格和服务条款版本，并记录用户付款前确认条款的时间。
  • 统一实现 grant_membership_days：加天从当前时间与原到期时间中较晚者计算，所有入口共用。
  • 管理员可快捷发放 30 / 365 天，也可填自定义天数或目标日期；目标日期按 Asia/Shanghai 当日结束保存。
  • 发放类型区分体验、赠送、补偿、测试和纠错；原因必填，请求 ID 唯一，防止重复点击多加天。
  • 不允许用负数天数撤销；退款、撤销和纠错走独立流程，记录应退、实退、剩余权益、理由和完整审计。
  • 服务端校验管理员权限，不允许前端直接修改数据库；每次变更记录操作者、对象、前后值、来源和时间。
  • 资源计费按处理后的实际字节；上传、替换和删除都更新额度，并设置不依赖会员承诺的安全硬上限。

进入下一阶段

免费 / 体验 / 年费权益可由服务端可靠执行，管理员能安全发放，用户能看到状态和用量；商品权益快照、条款确认、退款及停服善后也已可执行。

4 用留存、访谈与候补名单完成会员方案定案 本阶段仍不收钱；确定何时具备办理主体和接入官方虚拟支付的条件。 非付费商业验证

内部形成收费方案，但暂不开放购买

  • 公测至少运行 30～45 天，并出现约 15～20 名跨周重复完成核心记录的用户后，才开始深入讨论会员方案。
  • 先根据真实记录量、文件空间、流量和高价值功能确定基础版与会员版边界，不能为了收费人为破坏基础版。
  • 访谈高留存用户目前如何解决问题、最舍不得失去什么、替代方案花费多少时间或金钱，以及停止使用的原因。
  • 可以邀请用户加入“首批会员方案访谈／候补名单”，记录是否愿意继续了解；不收订金、不生成支付订单、不承诺最终价格。
  • 只有用户已经获得核心价值后，才在一对一研究中讨论 49、69～79 或其他内部价格假设；不在小程序、公测笔记或公开页面展示候选金额。
  • 汇总留存、候补意愿、拒绝原因、资源成本和预计维护时间；条件不足就继续公测补充数据，条件达到后启动个体工商户／其他合适主体的办理，未来推出付费会员的决定不变。
  • 当前不通过淘宝、小红书、闲鱼、个人转账或兑换码出售本小程序 VIP，也不把人工加 365 天作为真实付款验证。

意向和候补名单只能证明用户愿意继续了解，不能替代真实付款证据。49 元仍只是未来接入官方支付后的候选验证价，不是当前报价、长期价或终身价。

进入下一阶段

免费版边界、会员价值、候选价格和成本已能解释，并达到启动主体与官方支付准备的门槛；若尚未达到，就停留在本阶段继续公测，不改变未来收费方向。

官方虚拟支付接入与首批订单

  • 完成个体工商户或其他合适主体、小程序认证、服务类目和虚拟支付开通条件核对；优先保留现有 AppID 和用户体系。
  • 按届时官方接入指引使用小程序虚拟支付，不用普通小程序支付、外部店铺、个人收款或兑换码替代 VIP 购买链路。
  • 服务端创建 wechat_virtual_pay 待支付订单。前端成功提示不能直接增加会员，必须依据可信的平台订单结果履约。
  • 履约前核对 AppID、平台订单号、商品、金额／代币、支付状态和签名；主动查单与回调重复到达时仍只增加一次权益。
  • 公测期持续说明未来一定会收费；具体方案定案后，内部默认至少提前 7 天公布基础版边界、会员权益、价格、期限、不自动续费、退款规则、已有数据和停服处理。

  • 先积累约 20～50 笔真实官方订单，记录“已获得核心价值且看过报价的用户 → 购买”的转化、拒绝、退款、成本和客服时间。

  • 广告只放在列表底部、结果页等自然停顿处，不放在编辑、上传、弹窗和私人数据详情中。

对外固定说明

“人类草稿目前处于公开测试阶段，现阶段可免费使用。正式运营后，我们会保留可正常使用的免费基础版，并推出付费会员；会员将提供更多容量或部分进阶能力。具体权益、价格和收费时间将根据公测期间的真实使用情况确定，并在开始收费前提前告知。无论是否购买会员，已有数据都不会因会员规则被删除，并可继续查看、导出和删除。”

  • 常驻位置放在“我的 / 关于”，页面可使用简短“公开测试”标识；用户查看空间用量或开始大量上传时，再展示完整说明。
  • 首次进入不使用强制弹窗，不把未来收费计划变成进入产品前的主要信息；先让用户理解产品价值。
  • 不得使用“永久免费”“所有功能永远免费”等承诺，也不在公测笔记中提前展示 49 元或其他候选金额。
  • 正式公布收费时，同时公布免费版仍能做什么、会员增加什么、已有数据如何处理、过渡期和售后规则，避免只公布一个价格。
  • 可以向老用户提供首期验证价或额外过渡权益，但不承诺“创始用户终身 49 元”，避免把尚未验证的价格永久锁死。

通知周期为什么不再固定为 30 天

  • 用户从进入公测开始就能看到“现阶段免费、正式运营后一定推出付费会员”，因此首次收费不是毫无预告的临时变更。
  • 首次收费仍会新增具体价格、免费版边界和会员权益，内部默认在生效前至少 7 天完整公告，给活跃用户阅读和处理已有数据的时间；这是运营缓冲，不是对外固定承诺或统一法定期限。
  • 若本次调整会显著影响大量活跃用户，可以主动把过渡期延长到 14 天或更久，不必写死在长期对外文案中。
  • 国家层面的 30 天明确要求主要对应经营者决定停业或迁移服务场所。计划停运和已付费用户善后仍保留 30 天规则，不能与首次推出会员混为一谈。

进入收费准备前的最低条件

  • 至少完成一轮 30～45 天真实使用观察，而不是只看注册人数。
  • 出现约 15～20 名在多个自然周重复完成核心记录的用户，能够说明他们最舍不得失去的能力和现有替代方式。
  • 已经得到主要记录数、图片字节、空间和流量的分布，能解释免费版与会员版的边界，而不是人为制造限制。
  • 先访谈用户解决了什么问题、替代什么工具、停止使用会怎样，并通过无订金候补名单观察继续了解意愿。
  • 上述信号足以支持办理合适主体和接入官方虚拟支付的成本；若不成立，继续免费公测。

启动真实收费前的额外门槛

  • 会员、订单、权益快照、服务条款、退款处理和停服善后已经实现并验证。
  • 主体、小程序认证、服务类目和官方虚拟支付能力均满足届时要求，并按实际技术服务费重新计算价格。
  • 基础版边界、会员权益、价格和过渡规则已经定案；内部默认至少提前 7 天向现有用户公告，若变化影响较大可主动延长。
  • 不把口头意愿当作成交；接入后仍需以首期约 20～50 笔真实官方订单复核价格和模式。

心理依据：价格为零会产生超出普通降价的“零价格效应”，免费用户数量不能直接外推成付费需求；在没有事先说明和免费退路时突然从免费强制转收费，会损害公平感、信任和购买意愿。当前策略不是隐藏商业计划，而是先披露收费方向和用户保障，暂缓披露尚未验证的具体金额。

体验和到期规则

  • 公开测试与 30 天测试体验是两个状态。公测期所有用户使用统一公测权益；30 天体验只在会员底座、正式免费版边界和到期降级流程完成后启用。
  • 测试体验不是注册门槛；正式启用后如需发放，由管理员按用户 ID 手工增加 30 天权益，并记录发放人、原因、时间和完整审计日志。
  • 体验到期自动转为基础版，已有数据不删除。若空间超额，只暂停新增文件，仍可查看、下载、导出、删除，并可编辑不增加资源占用的文字。
  • 年度会员按单次购买处理，当前不自动续费。提前续费从 max（当前时间，原到期时间） 再增加 365 天。

退款与售后边界（收费前必须实现）

运营目标是防止用户在权益已经正常开通后，仅因个人偏好、长期闲置或忘记使用而随意要求退款；但不能写成“购买后任何情况一律不退”。年度会员需要持续提供 365 天服务，按预付式服务设计合同、订单和善后流程更稳妥。

  • 原则上不支持的情形：只有在用户付款前确实获得过与所购会员实质相同的服务、权益已正常开通，并且法律和交易平台规则允许时，才对仅因个人偏好变化、使用频率低、忘记使用或找到其他工具提出的无理由退款进行限制。
  • 必须受理的情形：重复支付、付款后未开通、开通对象错误且尚未使用、实际权益与商品描述明显不符、长期无法使用、开发者无法继续按约提供服务，以及法律法规或交易平台判定应退款。
  • 短时故障：优先恢复服务并按影响范围延长权益或给予补偿；不能用补偿替代用户依法享有的退款权。
  • 付费期内变更：年度会员有效期内不单方涨价或缩减用户购买时的权益；如确实无法继续履行，应提供继续履行、合理补偿或退款方案。
  • 计划停运：至少提前 30 天公告并停止继续收取可能无法履行的预付款；无法继续履行时，按尚未履行的剩余期限和实际成交金额计算应退余额，并保留用户导出数据的合理时间。
  • 内部退款基线：重复付款、未开通或未履约的订单全额退；已开始履约但因开发者原因终止时，建议退款基线为“实际成交金额 × 未履行自然日 ÷ 365”。法律或平台要求的金额更高时，以其规则为准。
  • 退款执行：由独立退款流程处理订单状态、剩余权益、退款金额和权益流水，不允许直接删除订单、修改历史成交金额或用负数天数掩盖退款。
  • 证据记录：保存商品权益快照、服务条款版本、用户确认时间、订单号、成交金额、开通时间、到期时间、实际使用状态、退款原因、处理结果和平台争议编号。

满足“付款前已获得实质相同服务”且交易平台规则允许时，才可采用的对外售后文案：“本商品为即时开通的年度数字服务。购买前可体验与本商品实质相同的核心服务。权益开通后，原则上不支持因个人偏好、闲置或忘记使用提出的无理由退款；重复支付、未开通、无法按约提供服务、实际权益与商品描述明显不符，以及法律法规或交易平台要求退款的情形除外。”

按 2026-08-13 的规则记录：预付式服务应在付款前明确服务内容、价格、期限、退费方式和违约责任。最高人民法院关于预付式消费的司法解释原则上支持消费者付款后七日内请求返还预付款，但购买前已经从经营者或其他经营者获得过相同商品或服务的除外。公测期的完整体验可能有助于证明用户了解相同核心服务，但若付费会员增加了未体验过的容量或功能，就不能当然认为属于完全相同服务；卖家自定文案也不能对抗法律或平台调处。

退款仍待讨论的问题

  • 公测权益与首期付费权益是否实质相同？如果会员增加了更多容量或新功能，是否应默认保留付款后七日的退款入口？
  • 用户已经消耗大量新增容量、第三方付费额度或一次性服务时，退款金额如何计算并在付款前清楚说明？
  • 退款申请入口、客服联系方式、响应时限和微信官方支付争议处理由谁负责？1～2 人维护时，什么承诺是长期做得到的？
  • 若项目停运、主体变化或支付渠道迁移，用户剩余期限、导出窗口和退款资金如何预留？

二、订单履约、管理员发放与身份迁移

当前启用范围：公测期不创建付费订单，不导入淘宝、小红书、闲鱼或个人转账订单。系统可以提前建好，但只使用 public_beta、测试、赠送和故障补偿等非交易权益。

最小数据结构

  • membership_products 保存商品与购买时的名称、天数、价格、权益快照；后续调价不改变历史订单。
  • user_memberships 每个用户一行，保存当前方案、体验开始时间和权益到期时间。
  • membership_orders 保存内部订单号、用户、商品、支付渠道、整数最小货币单位金额、状态、平台交易号、权益快照、服务条款版本、用户确认时间和支付／履约／退款时间。
  • membership_grants 是只追加的权益流水，记录购买、体验、赠送、补偿、撤销、退款和纠错。
  • membership_refunds 保存退款请求、关联订单、申请来源、原因、应退与实退金额、剩余权益处理、平台争议编号、操作者和状态；退款请求 ID 必须唯一。
  • membership_terms 保存可追溯的服务条款版本、生效时间和正文摘要。订单只引用购买当时版本，后续修改不能覆盖历史记录。
  • 会员、订单、退款和权益流水都通过稳定的 app_users.id 关联用户，不使用昵称、头像或 OpenID 人工匹配。

管理员工具

  • “官方订单查询／售后”和“测试、赠送、补偿发放”必须是两个入口；非交易发放不能伪装成订单或收入。
  • 公测期只开放非交易发放。查询用户后先展示昵称、用户 ID、当前身份、到期时间和已用空间，避免发错账号。
  • 自定义发放可选 30／365 天、自定义天数或目标日期，类型和原因必填；付费订单只能由可信支付结果触发固定商品权益。
  • 目标日期按 Asia/Shanghai 当日结束保存；不允许负数。缩短、撤销、退款走独立操作。
  • 提交前用全局 app-dialog 展示目标用户、原因和调整前后时间。服务端再次校验管理员、用户和参数。
  • 每次操作使用唯一请求 ID；重复点击、网络重试、重复订单回调不能重复加天。成功后返回可查询的流水编号。
  • 退款入口必须先展示原订单、成交金额、已使用期限、建议退款金额、退款后权益和数据影响，再确认提交；不能把“退款”混入普通的赠送或纠错入口。

统一订单履约

  1. 公测期没有付费订单；所有公测用户统一使用 public_beta，测试或补偿权益通过独立发放流水处理。
  2. 未来由服务端创建 wechat_virtual_pay 待支付订单，小程序前端只发起官方流程，不凭前端成功提示直接增加会员。
  3. 服务端依据可信的平台回调或主动查单结果，核对 AppID、平台订单号、商品、金额／代币、状态和签名。
  4. 核对成功后原子地把订单更新为已支付，并调用统一的 fulfill_membership_order；履约函数增加 365 天并写入权益流水。
  5. 订单 ID、平台订单号和请求 ID都必须幂等；回调、查单和网络重试重复发生时直接返回原结果。

外部店铺订单、个人转账和付费兑换码不进入当前履约方案。只有未来确实存在可独立使用的 App／网站服务，并就已有账号权益同步取得微信书面确认后，才另行设计跨端权益来源；不能复用普通管理员发放把它伪装成赠送。

主体或 AppID 变化

所有会员、订单和个人记录继续关联稳定的内部 app_users.id，不直接依赖 OpenID。逐步建立 auth_identities，用 provider＋app_id＋openid 唯一映射内部用户，并保存可取得的 UnionID。若以后必须更换 AppID，应通过旧账号登录确认、一次性迁移凭证或人工核验用户 ID 与历史订单安全绑定，不能仅凭昵称自动合并。

按 2026-08-13 的官方接入条件，虚拟支付要求已认证小程序，主体为企业、事业单位或个体工商户，个人主体不在当前可开通范围内。虚拟支付技术服务费不能套用普通小程序支付的常见费率；办理主体和接入时必须以当时后台展示的终端、类目和优惠费率重新计算。

三、成本模型与盈利判断

以下是缺少真实账单和真实用户数据时的保守模型，不代表已经发生的账单。汇率暂按 1 美元约 7.2 元人民币作为内部压力测试假设，正式复盘时应替换为实际账单汇率。

价格决策状态：49 元合理，但只适合作为验证起点

产品由个人开发、预计只有 1～2 人长期维护，确实能降低固定工资和管理开销，但不能把维护时间当成零成本。用户是否愿意付费，主要取决于产品替代了什么、记录和习惯有多重要、数据是否可信及能否安全迁移，而不是维护团队人数。当前对 49 元的判断需要按经营目标拆开：

内部价格假设适合验证什么当前判断
49 元 / 365 天官方虚拟支付接入后，用户是否愿意进行一笔低风险真实付款；能否覆盖基础设施可作为首期 20～50 笔官方订单的候选价；若目标是可持续副业收入，单价偏低，不能直接定成长期价
69～79 元 / 365 天在价值与信任已形成后，较可持续的个人工具价格带仅作后续内部研究区间；需用高留存用户访谈、真实转化、续费和成本支持，不在公测期展示
99 元 / 365 天或更高高频使用、数据沉淀或明显替代其他付费工具的用户价值现在没有证据；只有核心价值、持续运营信任和导出保障都成立后才讨论

以上不是同时上线三个价格，也不是预设将来一定涨价。公测期不成交；未来完成主体和官方虚拟支付后，同一公开批次使用同一商品和价格，不对条件相同的用户暗中随机报价。若以后测试不同价格，应采用时间或公开批次清晰分隔，并完整保留当时的商品、权益和价格快照。

49 元候选价的贡献空间

  • 按普通付费用户每年约 8 元资源成本粗算，每名 49 元会员在扣除资源后最多剩约 41 元；再扣官方虚拟支付技术服务费、税费、退款、客服和维护时间后会更少。虚拟支付费率不能按普通支付费率估算。
  • 100 名付费用户最多形成约 4100 元资源后贡献，主要只能覆盖当前固定基础设施；500 名约 20500 元，仍未计免费用户成本和 1～2 人的维护劳动。
  • 因此，如果目标只是让自己长期使用并覆盖服务器，49 元可能成立；如果目标是稳定副业收入，49 元更适合首期验证价，长期价格要结合规模、转化、续费和实际工时重新决定。

价格验证顺序

  1. 先看用户是否在 30～45 天内反复使用、最常使用哪个模块、保存了多少真实记录，以及哪里产生了持续价值。
  2. 访谈高留存用户时，先问目前怎么解决、替代方案花多少钱／时间、最舍不得失去哪项能力、为什么继续使用；不要一上来只问“49 元你愿不愿意”。
  3. 权益边界形成后，可邀请高留存用户参加会员方案访谈或无订金候补名单；候补和口头价格意愿只用于判断何时启动主体办理，不能当作成交。
  4. 完成合适主体、官方虚拟支付、退款与条款后，再向已经获得核心价值的用户展示完整报价，收集“看过报价 → 官方购买”的转化和拒绝原因。
  5. 首期积累约 20～50 笔真实官方订单后，联合复盘获客来源、激活、留存、转化、退款、客服时间、虚拟支付费率、单用户成本和续费意向，再决定 49 元是否保留、上调或重新设计权益。

仍待讨论的问题

  • 正式基础版最小可用范围是什么，哪些容量或进阶能力放入会员后不会让免费用户感觉数据被扣住？
  • 首期验证的核心目标是覆盖固定成本、验证付款意愿，还是追求可持续副业收入？目标不同，49 元是否合理的结论也不同。
  • 开发、客服、内容审核和故障处理每月实际投入多少小时？应把多少维护时间计入长期价格，而不是只看现金账单？
  • 用户最在意的是容量、效率、跨模块整合、无广告、数据安全还是长期运营承诺？这个答案将决定会员卖点，而不只是决定数字大小。

四、推广前保护、监控与首轮验证指标

统一资源计量

  • 按用户统计文件总字节和文件数，并可按模块拆分；上传前按处理后的真实大小检查额度。
  • 替换只计算新旧差值，删除同步释放额度；定期核对数据库、额度计数器和 Storage 对象，处理孤儿文件与错误计数。
  • 后台观察总量与单用户 P50、P90、P99、最高占用量。

图片与访问保护

  • 限制最长边、总像素和单文件大小；普通图片不超过 5 MB并使用有损 WebP。所有业务模块只保存一张受限高清图，由列表、详情、预览和打印共用，不生成缩略图。
  • 个人图片使用私有 Bucket 或受控短期地址，官方公共素材与用户素材分离；替换、删除记录时清理当前文件，并兼容清理由旧版本可能留下的派生路径。
  • 历史图片迁移必须可重复执行，迁移后核对对象数、总字节和页面显示；限制输入像素，防止超大图片或解压炸弹。

反滥用与安全

  • 按免费／体验／会员设置每日上传文件数、上传总字节、接口频率与安全硬上限；所有列表分页并限制返回条数，高频查询补齐以 user_id 为首列的索引。
  • 禁止自动化写入、共享链接或外链托管；异常上传、下载和写入触发告警与临时冻结。
  • 关键文字和图片写入经过内容安全检查；验证数据库备份与恢复，准备严重故障处理方式。
  • 提供隐私说明、账号注销、个人数据删除和基础导出；正式收费前补齐会员服务、退款、合理使用和隐私规则。

每月成本与盈利监控

  • 记录活跃用户、付费用户、各方案收入、退款、数据库大小、存储、缓存／非缓存流量、计算规格和真实账单。
  • 分开观察体验、免费和年费用户，计算每个付费活跃用户的月均基础设施成本和毛利。
  • 年度会员达到 10、25、50、100 人时复盘；免费空间、会员空间和价格只在取得 30～60 天真实数据后调整。

首轮验证指标

  • D7、D30 活跃与留存，单模块／跨模块比例，每位活跃用户的主要记录数。
  • 每用户图片数、存储字节、月访问流量，以及免费用户遇到记录或高级功能限制的位置。
  • 已经获得核心价值的用户真实看到首期候选价格后的购买选择、拒绝原因、年度会员续费率和提前续费比例。
  • 体验、免费、年费用户的真实资源成本差异。公开测试阶段不以总注册人数作为核心指标。
