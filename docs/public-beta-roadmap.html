上传保护与成本取舍

  • 服务端把普通图片上传硬上限设为 5 MB；即使环境配置误设得更高，也不会越过该上限。小程序裁剪后的正常图片通常低于此值，超过时提示用户缩小后重试。
  • 服务端在解码前限制图片总像素为 5,000 万，防止尺寸异常但压缩包很小的图片消耗过多内存。客户端裁剪不能替代这项服务端保护。
  • 所有规格都只缩小、不放大小图。WebP 使用有损颜色压缩，但透明通道使用更高质量，避免透明菜图边缘明显劣化。
  • 没有为菜品增加 720 像素缩略图：当前优先降低 Storage 增长；上线后再依据实际列表下载流量决定是否增加 360～480 像素小图。

  1. 保存失败、数据错误、隐私和性能问题。
  2. 阻碍用户完成核心流程的体验问题。
  3. 高频用户真实提出的功能改进。
  4. 新的模块灵感和低优先级美化。

必须观察

  • D7、D30 留存，以及用户回来使用的频率。
  • 单模块用户和跨模块用户的比例。
  • 每个模块主要记录数的 P50 / P80 / P90，用来制定免费数量限制。
  • 每用户图片数、处理后实际字节数、数据库容量、下载流量和月成本。
  • 用户在哪些高级能力上真正感受到价值。
  • 重度与异常用户是否触发单文件、每日上传、接口频率和总空间保护。

同期完成的成本保护

  • 图片限制最大边长和总像素，使用有损 WebP；已有缩略图的模块在列表中优先加载缩略图。菜品当前只保留一张 1536 像素打印图，是否增加小缩略图由实际流量决定。
  • 替换和删除文件时正确释放额度，定期对账孤儿文件，并为历史图片安排兼容迁移。
  • 按用户和模块核算文件空间，查询分页并补齐 user_id 索引；私有文件使用受控访问。

至少取得一轮 30～45 天真实使用数据，能够识别核心用户和主要成本来源。

  • 按真实数据确定每个模块的“主要记录”免费上限；不是每使用一次扣费，也不拆成逐模块购买。

通知周期为什么不再固定为 30 天

  • 用户从进入公测开始就能看到“现阶段免费、正式运营后一定推出付费会员”，因此首次收费不是毫无预告的临时变更。
  • 首次收费仍会新增具体价格、免费版边界和会员权益，内部默认在生效前至少 7 天完整公告，给活跃用户阅读和处理已有数据的时间；这是运营缓冲，不是对外固定承诺或统一法定期限。
  • 若本次调整会显著影响大量活跃用户，可以主动把过渡期延长到 14 天或更久，不必写死在长期对外文案中。
  • 国家层面的 30 天明确要求主要对应经营者决定停业或迁移服务场所。计划停运和已付费用户善后仍保留 30 天规则，不能与首次推出会员混为一谈。

  • 至少完成一轮 30～45 天真实使用观察，而不是只看注册人数。
  • 出现约 15～20 名在多个自然周重复完成核心记录的用户，能够说明他们最舍不得失去的能力和现有替代方式。
  • 已经得到主要记录数、图片字节、空间和流量的分布，能解释免费版与会员版的边界，而不是人为制造限制。
  • 先访谈用户解决了什么问题、替代什么工具、停止使用会怎样，并通过无订金候补名单观察继续了解意愿。
  • 上述信号足以支持办理合适主体和接入官方虚拟支付的成本；若不成立，继续免费公测。

启动真实收费前的额外门槛

  • 会员、订单、权益快照、服务条款、退款处理和停服善后已经实现并验证。
  • 主体、小程序认证、服务类目和官方虚拟支付能力均满足届时要求，并按实际技术服务费重新计算价格。
  • 基础版边界、会员权益、价格和过渡规则已经定案；内部默认至少提前 7 天向现有用户公告，若变化影响较大可主动延长。
  • 不把口头意愿当作成交；接入后仍需以首期约 20～50 笔真实官方订单复核价格和模式。

心理依据：价格为零会产生超出普通降价的“零价格效应”，免费用户数量不能直接外推成付费需求；在没有事先说明和免费退路时突然从免费强制转收费，会损害公平感、信任和购买意愿。当前策略不是隐藏商业计划，而是先披露收费方向和用户保障，暂缓披露尚未验证的具体金额。

体验和到期规则

  • 公开测试与 30 天测试体验是两个状态。公测期所有用户使用统一公测权益；30 天体验只在会员底座、正式免费版边界和到期降级流程完成后启用。

  • 体验到期自动转为基础版，已有数据不删除。若空间超额，只暂停新增文件，仍可查看、下载、导出、删除，并可编辑不增加资源占用的文字。
  • 年度会员按单次购买处理，当前不自动续费。提前续费从 max（当前时间，原到期时间） 再增加 365 天。

退款与售后边界（收费前必须实现）

运营目标是防止用户在权益已经正常开通后，仅因个人偏好、长期闲置或忘记使用而随意要求退款；但不能写成“购买后任何情况一律不退”。年度会员需要持续提供 365 天服务，按预付式服务设计合同、订单和善后流程更稳妥。

  • 原则上不支持的情形：只有在用户付款前确实获得过与所购会员实质相同的服务、权益已正常开通，并且法律和交易平台规则允许时，才对仅因个人偏好变化、使用频率低、忘记使用或找到其他工具提出的无理由退款进行限制。
  • 必须受理的情形：重复支付、付款后未开通、开通对象错误且尚未使用、实际权益与商品描述明显不符、长期无法使用、开发者无法继续按约提供服务，以及法律法规或交易平台判定应退款。
  • 短时故障：优先恢复服务并按影响范围延长权益或给予补偿；不能用补偿替代用户依法享有的退款权。
  • 付费期内变更：年度会员有效期内不单方涨价或缩减用户购买时的权益；如确实无法继续履行，应提供继续履行、合理补偿或退款方案。
  • 计划停运：至少提前 30 天公告并停止继续收取可能无法履行的预付款；无法继续履行时，按尚未履行的剩余期限和实际成交金额计算应退余额，并保留用户导出数据的合理时间。
  • 内部退款基线：重复付款、未开通或未履约的订单全额退；已开始履约但因开发者原因终止时，建议退款基线为“实际成交金额 × 未履行自然日 ÷ 365”。法律或平台要求的金额更高时，以其规则为准。
  • 退款执行：由独立退款流程处理订单状态、剩余权益、退款金额和权益流水，不允许直接删除订单、修改历史成交金额或用负数天数掩盖退款。
  • 证据记录：保存商品权益快照、服务条款版本、用户确认时间、订单号、成交金额、开通时间、到期时间、实际使用状态、退款原因、处理结果和平台争议编号。

满足“付款前已获得实质相同服务”且交易平台规则允许时，才可采用的对外售后文案：“本商品为即时开通的年度数字服务。购买前可体验与本商品实质相同的核心服务。权益开通后，原则上不支持因个人偏好、闲置或忘记使用提出的无理由退款；重复支付、未开通、无法按约提供服务、实际权益与商品描述明显不符，以及法律法规或交易平台要求退款的情形除外。”

按 2026-08-13 的规则记录：预付式服务应在付款前明确服务内容、价格、期限、退费方式和违约责任。最高人民法院关于预付式消费的司法解释原则上支持消费者付款后七日内请求返还预付款，但购买前已经从经营者或其他经营者获得过相同商品或服务的除外。公测期的完整体验可能有助于证明用户了解相同核心服务，但若付费会员增加了未体验过的容量或功能，就不能当然认为属于完全相同服务；卖家自定文案也不能对抗法律或平台调处。

退款仍待讨论的问题

  • 公测权益与首期付费权益是否实质相同？如果会员增加了更多容量或新功能，是否应默认保留付款后七日的退款入口？
  • 用户已经消耗大量新增容量、第三方付费额度或一次性服务时，退款金额如何计算并在付款前清楚说明？
  • 退款申请入口、客服联系方式、响应时限和微信官方支付争议处理由谁负责？1～2 人维护时，什么承诺是长期做得到的？
  • 若项目停运、主体变化或支付渠道迁移，用户剩余期限、导出窗口和退款资金如何预留？

二、订单履约、管理员发放与身份迁移

当前启用范围：公测期不创建付费订单，不导入淘宝、小红书、闲鱼或个人转账订单。系统可以提前建好，但只使用 public_beta、测试、赠送和故障补偿等非交易权益。

最小数据结构

  • membership_products 保存商品与购买时的名称、天数、价格、权益快照；后续调价不改变历史订单。
  • user_memberships 每个用户一行，保存当前方案、体验开始时间和权益到期时间。
  • membership_orders 保存内部订单号、用户、商品、支付渠道、整数最小货币单位金额、状态、平台交易号、权益快照、服务条款版本、用户确认时间和支付／履约／退款时间。
  • membership_grants 是只追加的权益流水，记录购买、体验、赠送、补偿、撤销、退款和纠错。
  • membership_refunds 保存退款请求、关联订单、申请来源、原因、应退与实退金额、剩余权益处理、平台争议编号、操作者和状态；退款请求 ID 必须唯一。
  • membership_terms 保存可追溯的服务条款版本、生效时间和正文摘要。订单只引用购买当时版本，后续修改不能覆盖历史记录。
  • 会员、订单、退款和权益流水都通过稳定的 app_users.id 关联用户，不使用昵称、头像或 OpenID 人工匹配。

管理员工具

  • “官方订单查询／售后”和“测试、赠送、补偿发放”必须是两个入口；非交易发放不能伪装成订单或收入。
  • 公测期只开放非交易发放。查询用户后先展示昵称、用户 ID、当前身份、到期时间和已用空间，避免发错账号。
  • 自定义发放可选 30／365 天、自定义天数或目标日期，类型和原因必填；付费订单只能由可信支付结果触发固定商品权益。
  • 目标日期按 Asia/Shanghai 当日结束保存；不允许负数。缩短、撤销、退款走独立操作。
  • 提交前用全局 app-dialog 展示目标用户、原因和调整前后时间。服务端再次校验管理员、用户和参数。
  • 每次操作使用唯一请求 ID；重复点击、网络重试、重复订单回调不能重复加天。成功后返回可查询的流水编号。
  • 退款入口必须先展示原订单、成交金额、已使用期限、建议退款金额、退款后权益和数据影响，再确认提交；不能把“退款”混入普通的赠送或纠错入口。

统一订单履约

  1. 公测期没有付费订单；所有公测用户统一使用 public_beta，测试或补偿权益通过独立发放流水处理。
  2. 未来由服务端创建 wechat_virtual_pay 待支付订单，小程序前端只发起官方流程，不凭前端成功提示直接增加会员。
  3. 服务端依据可信的平台回调或主动查单结果，核对 AppID、平台订单号、商品、金额／代币、状态和签名。
  4. 核对成功后原子地把订单更新为已支付，并调用统一的 fulfill_membership_order；履约函数增加 365 天并写入权益流水。
  5. 订单 ID、平台订单号和请求 ID都必须幂等；回调、查单和网络重试重复发生时直接返回原结果。

外部店铺订单、个人转账和付费兑换码不进入当前履约方案。只有未来确实存在可独立使用的 App／网站服务，并就已有账号权益同步取得微信书面确认后，才另行设计跨端权益来源；不能复用普通管理员发放把它伪装成赠送。

主体或 AppID 变化

所有会员、订单和个人记录继续关联稳定的内部 app_users.id，不直接依赖 OpenID。逐步建立 auth_identities，用 provider＋app_id＋openid 唯一映射内部用户，并保存可取得的 UnionID。若以后必须更换 AppID，应通过旧账号登录确认、一次性迁移凭证或人工核验用户 ID 与历史订单安全绑定，不能仅凭昵称自动合并。

按 2026-08-13 的官方接入条件，虚拟支付要求已认证小程序，主体为企业、事业单位或个体工商户，个人主体不在当前可开通范围内。虚拟支付技术服务费不能套用普通小程序支付的常见费率；办理主体和接入时必须以当时后台展示的终端、类目和优惠费率重新计算。

三、成本模型与盈利判断

以下是缺少真实账单和真实用户数据时的保守模型，不代表已经发生的账单。汇率暂按 1 美元约 7.2 元人民币作为内部压力测试假设，正式复盘时应替换为实际账单汇率。

价格决策状态：49 元合理，但只适合作为验证起点

产品由个人开发、预计只有 1～2 人长期维护，确实能降低固定工资和管理开销，但不能把维护时间当成零成本。用户是否愿意付费，主要取决于产品替代了什么、记录和习惯有多重要、数据是否可信及能否安全迁移，而不是维护团队人数。当前对 49 元的判断需要按经营目标拆开：

内部价格假设适合验证什么当前判断
49 元 / 365 天官方虚拟支付接入后，用户是否愿意进行一笔低风险真实付款；能否覆盖基础设施可作为首期 20～50 笔官方订单的候选价；若目标是可持续副业收入，单价偏低，不能直接定成长期价
69～79 元 / 365 天在价值与信任已形成后，较可持续的个人工具价格带仅作后续内部研究区间；需用高留存用户访谈、真实转化、续费和成本支持，不在公测期展示
99 元 / 365 天或更高高频使用、数据沉淀或明显替代其他付费工具的用户价值现在没有证据；只有核心价值、持续运营信任和导出保障都成立后才讨论

以上不是同时上线三个价格，也不是预设将来一定涨价。公测期不成交；未来完成主体和官方虚拟支付后，同一公开批次使用同一商品和价格，不对条件相同的用户暗中随机报价。若以后测试不同价格，应采用时间或公开批次清晰分隔，并完整保留当时的商品、权益和价格快照。

49 元候选价的贡献空间

  • 按普通付费用户每年约 8 元资源成本粗算，每名 49 元会员在扣除资源后最多剩约 41 元；再扣官方虚拟支付技术服务费、税费、退款、客服和维护时间后会更少。虚拟支付费率不能按普通支付费率估算。
  • 100 名付费用户最多形成约 4100 元资源后贡献，主要只能覆盖当前固定基础设施；500 名约 20500 元，仍未计免费用户成本和 1～2 人的维护劳动。
  • 因此，如果目标只是让自己长期使用并覆盖服务器，49 元可能成立；如果目标是稳定副业收入，49 元更适合首期验证价，长期价格要结合规模、转化、续费和实际工时重新决定。

价格验证顺序

  1. 先看用户是否在 30～45 天内反复使用、最常使用哪个模块、保存了多少真实记录，以及哪里产生了持续价值。
  2. 访谈高留存用户时，先问目前怎么解决、替代方案花多少钱／时间、最舍不得失去哪项能力、为什么继续使用；不要一上来只问“49 元你愿不愿意”。
  3. 权益边界形成后，可邀请高留存用户参加会员方案访谈或无订金候补名单；候补和口头价格意愿只用于判断何时启动主体办理，不能当作成交。
  4. 完成合适主体、官方虚拟支付、退款与条款后，再向已经获得核心价值的用户展示完整报价，收集“看过报价 → 官方购买”的转化和拒绝原因。
  5. 首期积累约 20～50 笔真实官方订单后，联合复盘获客来源、激活、留存、转化、退款、客服时间、虚拟支付费率、单用户成本和续费意向，再决定 49 元是否保留、上调或重新设计权益。

仍待讨论的问题

  • 正式基础版最小可用范围是什么，哪些容量或进阶能力放入会员后不会让免费用户感觉数据被扣住？
  • 首期验证的核心目标是覆盖固定成本、验证付款意愿，还是追求可持续副业收入？目标不同，49 元是否合理的结论也不同。
  • 开发、客服、内容审核和故障处理每月实际投入多少小时？应把多少维护时间计入长期价格，而不是只看现金账单？
  • 用户最在意的是容量、效率、跨模块整合、无广告、数据安全还是长期运营承诺？这个答案将决定会员卖点，而不只是决定数字大小。

四、推广前保护、监控与首轮验证指标

统一资源计量

  • 按用户统计文件总字节和文件数，并可按模块拆分；上传前按处理后的真实大小检查额度。
  • 替换只计算新旧差值，删除同步释放额度；定期核对数据库、额度计数器和 Storage 对象，处理孤儿文件与错误计数。
  • 后台观察总量与单用户 P50、P90、P99、最高占用量。

图片与访问保护

  • 限制最长边、总像素和单文件大小；普通图片不超过 5 MB并使用有损 WebP。已有缩略图的模块在列表中优先加载缩略图；菜品现阶段不额外增加派生文件，保留一张受限高清图用于列表与打印。
  • 个人图片使用私有 Bucket 或受控短期地址，官方公共素材与用户素材分离；替换、删除记录时清理所有派生文件。
  • 历史图片迁移必须可重复执行，迁移后核对对象数、总字节和页面显示；限制输入像素，防止超大图片或解压炸弹。

反滥用与安全

  • 按免费／体验／会员设置每日上传文件数、上传总字节、接口频率与安全硬上限；所有列表分页并限制返回条数，高频查询补齐以 user_id 为首列的索引。
  • 禁止自动化写入、共享链接或外链托管；异常上传、下载和写入触发告警与临时冻结。
  • 关键文字和图片写入经过内容安全检查；验证数据库备份与恢复，准备严重故障处理方式。
